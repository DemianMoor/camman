# 03 — Data Model

_Last updated: 2026-09-04_

Schema lives in a single file: [`db/schema.ts`](../db/schema.ts) (~1,880 lines, Drizzle). Migrations are **hand-authored** SQL in [`db/migrations/`](../db/migrations/) (`0001`…`0070`). `db/schema.ts` is the Drizzle representation; where it lags a migration, **the migration is the DB source of truth** (see the rule-type notes below).

## Multi-tenant boundary

Every domain table carries `org_id UUID → organizations.id` and an index on it. **Every read/write filters by `org_id` in application code** (primary defense; RLS is secondary). The only tables without `org_id` are pure junctions whose parents are already org-scoped (`opt_out_brands`, `opt_out_providers`) and the external `auth.users` (Supabase-managed).

> **Performance indexes (migration `0078`) — additive only, no behavior change.** Five indexes backing existing hot query paths: `opt_outs(org_id, contact_id)` (suppression `EXISTS` probes — compliance-critical table, index only, no suppression-logic change); `stage_result_rows(org_id, created_at)` (the only large domain table that had no `org_id` index); `contacts(org_id, created_at)` (default million-row list sort/paginate); a **partial** `campaign_stages(scheduled_at) WHERE sent_at IS NULL AND schedule_missed_at IS NULL` (the `*/15` scheduled-send cron's due-and-unfired scan, [`lib/sends/scheduled.ts`](../lib/sends/scheduled.ts)); `campaigns(org_id, status)` ("active campaigns for this org"); and partial `stage_sends(org_id) WHERE status='sending'` (the `/api/sends/state` stuck-row `count(*)` that runs on every protected page — `stage_sends` already had `(org_id, sent_at)` for breaker accounting but nothing for the `status='sending'` probe).

> **Trigram phone-search indexes (migration `0088`) — additive only, no behavior change.** `pg_trgm` GIN indexes on `phone_number` for `contacts`, `opt_outs`, `opt_ins`, `clickers`, so the list-view substring search (`ILIKE '%digits%'`) is index-served instead of a full org-partition scan. A plain btree cannot serve a leading-wildcard match, so before this the contacts search **and** its mandatory `COUNT(*)` seq-scanned the whole table — measured at ~820 ms on 752K contacts, now ~3 ms (bitmap index scan). `pg_trgm` lives in the `extensions` schema (Supabase convention; already on the role `search_path`), referenced as `extensions.gin_trgm_ops`. The four indexes are declared in [`db/schema.ts`](../db/schema.ts) but not represented in the drizzle snapshot (managed in SQL, like `stage_sends`'s indexes). Built with `CREATE INDEX CONCURRENTLY` in prod to avoid a write lock; the migration's plain `CREATE INDEX IF NOT EXISTS` then no-ops. Sub-3-char search terms fall back to a scan (trigrams need 3 chars) — fine for phone digits.

> **Telnyx Number Lookup — carrier/line-type enrichment (migrations `0095`–`0098`).** Five new tables + `contacts`/`stage_sends` columns. See [04-features/phone-lookup-carrier.md](04-features/phone-lookup-carrier.md).
> - **`phone_lookups`** — GLOBAL cache (no `org_id`; carrier is a fact about a number). PK `phone` (E.164 `+1XXXXXXXXXX`, matches `contacts.phone_number`). Columns: `line_type` (`mobile`/`landline`/`voip`/`toll_free`/`unknown`), `carrier_raw`, `carrier_norm` (six buckets + `Unmapped`), `normalized_carrier` (Telnyx's own network-normalized name — chain step 1, migration 0104), `ocn`, `spid`, `ported`, `ported_date`, `source` (`telnyx`/`csv_import`/`manual_edit`/`dlr_inferred`), `lookup_status`, `retry_count`, `raw_response` (jsonb audit). Partial indexes: failed-retry sweep, unmapped queue.
> - **`carrier_mappings`** — global, seeded. PK `raw_name` → `carrier_norm` bucket (`mapped_by` records provenance: `seed`/`ai`/`human`/`admin`). Admin/AI assign unmapped strings; assignment retroactively updates `phone_lookups` + `contacts` (v2: on the normalized key, fixing all suffix variants).
> - **`carrier_patterns`** _(migration 0104)_ — global regex rules (`pattern`, `brand`, `priority`, `is_active`) matched against the normalized carrier key; resolver chain step 3 (fallback after exact mapping). Seeded with the majors.
> - **`carrier_classify_queue`** _(migration 0105)_ — distinct unresolved normalized carrier strings (PK `match_key`, `raw_example`, `status` ∈ `pending`/`ai_resolved`/`needs_human`/`human_resolved`, `confidence`, `attempts`, `last_error`) awaiting async AI triage. `contact_count` derived on read (never stored).
> - **`lookup_settings`** — account-global single row (boolean PK fixed `true`): `lookup_paused`, `lookup_daily_cap`, `lookup_rate_base`, `lookup_rate_mobile`, `lookup_concurrency_rps`, `worker_lease_until`, `carrier_resolver_v2` (chain feature flag, default false), `carrier_ai_run_cap` (triage per-run API-call breaker, default 200). Rates admin-editable (Telnyx has no pricing API).
> - **`carrier_norm_backfill_snapshot`** — created on demand by the v2 backfill (`scripts/backfill-carrier-v2.ts --apply`) to snapshot `contacts.carrier_norm` before recompute (rollback source).
> - **`lookup_group_stats_cache`** _(migration 0106)_ — per-org cache for the Lookup Stats Panel (PK `org_id`, `data` jsonb = the whole `{summary, groups[]}` blob, `computed_at`). The ~2s full-population coverage/suppression aggregate is cached here; the panel reads it in ~46ms. Written atomically (single upsert) so a failed refresh leaves the prior row intact. RLS: own-org SELECT (`current_org_id()`), server-only writes. Reversible/additive.
> - **`lookup_batches`** (org-scoped, reporting only) + **`lookup_queue`** (worker state, no `org_id`, claimed `FOR UPDATE SKIP LOCKED`).
> - **`contacts`** gains `line_type`, `carrier_norm` (default `Unidentified` = no `phone_lookups` row yet; migration 0099 split the former `Unknown` into `Unidentified` vs looked-up-but-`Unknown`), and `messaging_status` (`eligible`/`not_applicable`). `messaging_status` is the DB-enforced landline hard stop, derived by trigger `contacts_derive_messaging_status` (`line_type='landline' ⇒ not_applicable`, else `eligible`). Trigger, not a generated column, so `ADD COLUMN` is metadata-only (no rewrite at scale). Four **eligible-partial** indexes `(org_id[, …]) WHERE messaging_status='eligible'` back the hot paths (built concurrently via `scripts/apply-eligible-indexes-concurrent.ts`, 0088 pattern); the pre-existing non-partial indexes stay for the Contacts admin screen (the one place landlines remain visible). Every audience/segment/send query adds `AND messaging_status='eligible'`.
> - **`stage_sends`** gains `carrier_norm` (stamped at send time; future per-carrier analytics; no report reads it yet).
> - **`stage_sends`** gains `provider_phone_id` + `cost_per_sms` _(migration 0112)_ — durable reporting snapshots stamped at materialization from the stage's phone/rate, so per-number attribution and per-send cost survive later stage edits. **`provider_phone_id` was backfilled 2026-08-12** (`scripts/backfill-stage-send-provider-phone.ts`, idempotent) — 1,008,689 pre-0112 rows stamped from their `campaign_stages.provider_phone_id`, 0 NULLs remain; post-backfill per-phone totals matched the pre-backfill read-time `COALESCE` figures exactly, confirming it resolved the same way [`lib/reporting/rollup.ts`](../lib/reporting/rollup.ts) does. `provider_phone_id` is now fully populated org-wide — NULL only for rows that predate a future column change. `cost_per_sms` was **not** touched by this backfill; the reports rollup's `COALESCE(send snapshot, stage live value)` fallback still applies to it.
> - **RLS**: `phone_lookups`/`carrier_mappings`/`carrier_patterns`/`carrier_classify_queue`/`lookup_settings`/`lookup_queue` enabled **policy-less** (server-only, no org to scope — geoip_cache/`0066` pattern); `lookup_batches` org-scoped SELECT, no write policies (`0085` pattern).

## Conventions (CLAUDE.md §6)

- **IDs:** small lookup/registry tables use `serial` integer PKs; high-volume tables (`contacts`, `stage_sends`) use `uuid`; `links`/`clicks`/`send_circuit_events`/`campaign_events` use `bigserial`. Most registry tables also carry a separate **text business id** (`brand_id`, `offer_id`, `segment_id`, …) that is unique and user-facing.
- Every domain table has `created_at TIMESTAMPTZ DEFAULT now()`. Most have `status TEXT` + `archived_at TIMESTAMPTZ` (soft-delete via `status='archived'`).
- **Money:** `NUMERIC(12,4)`. **Timestamps:** `TIMESTAMPTZ` (UTC), never naive.
- Foreign keys are always declared; cascades are explicit (`cascade` / `restrict` / `set null` chosen per relationship).

## Tables by domain

### Tenancy & access
| Table | Key columns | Notes |
|-------|------------|-------|
| `organizations` | `id uuid` | the tenant root |
| `org_members` | `user_id→auth.users`, `org_id`, `role`, `is_active`, `last_login_at`, `last_login_ip`, `invited_email`, `invited_at` | UNIQUE(user_id, org_id); role CHECK in {owner,admin,manager,operator,viewer}. **`is_active` (migration 0175, default true)** is the deactivation switch, re-read on EVERY request inside the query that already resolves org_id + role, so it costs no extra round-trip and cuts access at the next request instead of at token expiry. `last_login_ip` is `text`, not `inet`: `x-forwarded-for` is a comma-separated list behind more than one proxy, which `inet` rejects. `invited_email`/`invited_at` are an audit record written at acceptance — they are NOT the invite mechanism, because `user_id` is NOT NULL with an FK to `auth.users`, so an `org_members` row cannot exist before the user does. | `invites` | `org_id`, `email`, `role`, `token` UNIQUE, `expires_at`, `accepted_at` | pending member invitations. Under Google sign-in **the row IS the authorization**: there is no password to set and no token for the invitee to carry, so `resolveAllowlist` simply looks for an open row matching the verified address. `token` is still populated (NOT NULL UNIQUE) so an emailed-link flow stays possible without a migration. `invites_role_check` excludes `owner`, so an invite can never mint one |

| `org_settings` | `org_id` PK, `sends_enabled` (default false), `sends_enabled_updated_by/_at`, `sends_paused` (default false), `sends_paused_at/_by` | per-org singleton; DB master switch for live SMS sending (migration 0063). `sends_paused` (migration 0080) is the dedicated **emergency hard-stop** flipped one-click from the Today's sends screen — independent of `sends_enabled`, halts the drain mid-run. | `org_setting_events` | `org_id`, `setting_key`, `old_value`, `new_value`, `actor_user_id` | append-only audit of settings flips (migration 0063) |

| `provider_route_aliases` | `org_id`, `sms_provider_id`, `credential_id` (nullable), `alias`, `created_at` | stable "Route A / B / C…" label per provider account (migration 0175, **Phase 2** — ships empty). Owner sees provider name + alias; Operator sees the alias only. **Two partial uniques, not one composite**: a plain `UNIQUE (org_id, sms_provider_id, credential_id)` would let unlimited rows through when `credential_id IS NULL`, because NULL never equals NULL in a unique index — so uniqueness is split on the null-ness. `UNIQUE (org_id, alias)` keeps the alias an identifier |
| `api_tokens` | `org_id`, `org_member_id` (cascade), `token_hash` UNIQUE, `token_prefix`, `name`, `read_only` (default true), `expires_at`, `last_used_at`, `revoked_at`, `created_by_user_id` (set null), `created_at` | personal bearer tokens (migration 0176, ClickUp 869evpmbz). **FK is `org_member_id`, not `user_id`** — the token's authority IS the membership, so removing someone from the org takes their tokens with it by CASCADE, and the auth resolver reads token + org + role + `is_active` + `api_enabled` in ONE join (matching the single round-trip a session costs). `token_hash` is SHA-256 hex and **the only copy** — the plaintext is shown once at creation and is not recoverable. Not bcrypt/argon2: the secret is 256 random bits, so there is nothing to stretch, and a slow KDF on a polled endpoint burns CPU seconds per wall-clock second. `token_prefix` is the non-secret leading characters, for telling two tokens apart in the UI. **Revoke is a stamp, not a delete** — the row survives so the usage history stays readable. `read_only` exists for a future write-capable token; nothing sets it false today, because WHAT a token may reach is decided by the `token` allowlist in `lib/authz/route-map.ts`, not by HTTP method |
| `api_token_usage` | `org_id`, `api_token_id` (cascade), `window_kind` ∈ {request, denied}, `window_start` (UTC hour), `count` | per-token hourly counters (migration 0176). UNIQUE `(api_token_id, window_kind, window_start)`; index `(org_id, window_start)` drives the per-user drill-in |
| `audience_fresh_counts` | `org_id` PK, `counts` jsonb, `computed_at`, `duration_ms`, `updated_at` | one-row-per-org rollup behind `GET /api/audience/fresh-counts` (migration 0176). Mirrors `contact_org_stats.carrier_breakdown`: a JSONB blob refreshed on a cron plus the timestamp the reader needs to state its own staleness. **The blob holds exactly what the endpoint returns — group NAMES and integers, no ids, no phones, no contact fields** — so nothing is stripped at the response boundary, because there is nothing there to strip. `computed_at` NULL means the cron has never run and the endpoint answers 503 rather than a misleading zero |

> **Multi-account provider credentials + encryption at rest (migration `0110`, applied 2026-07-16).** `provider_credentials` moved from one key per (provider, brand) to N accounts per provider — a row IS an account (`label`, `api_key_encrypted`, `api_key_last4`). `provider_phones.credential_id` (nullable FK, `ON DELETE SET NULL`) binds a sending number to the account it sends through; send-time key resolution walks number → account → key (`resolveKeyForStage`, [lib/sends/provider-credential.ts](../lib/sends/provider-credential.ts)). `api_key_encrypted` is AES-256-GCM ciphertext (`lib/crypto/secret-box.ts`), blob format `v1.<iv>.<ciphertext>.<authTag>`, keyed by env `PROVIDER_CREDENTIALS_KEY`. Plaintext `api_key` is retained, now nullable, for a **dual-read window** — `decryptCredentialKey` prefers the encrypted blob, falls back to plaintext — until a later, separately-gated migration `0112` drops the column (after `0111` tightens the new columns to `NOT NULL`; neither is applied yet). Backfill (`scripts/backfill-provider-credentials-encryption.ts`, applied 2026-07-16, idempotent) encrypted the 2 existing rows and linked each provider's phones to its sole credential. > **`supports_api_send` go-live gate moved off the bulk form (migration `0131`, ClickUp 869ehjwtf).** Widens the `send_circuit_events_event_check` CHECK to add `api_send_enabled` / `api_send_disabled`. Purely additive — writes no rows, and inert until the new `POST /api/providers/[providerId]/api-send` endpoint ships alongside it. No lock concern: the constraint is on `send_circuit_events`, not on a hot send path. Mirrors `0049`, which widened the clicks classification CHECK the same way. **Why:** the flag gates whether a provider may send live SMS at all, but was editable from the provider form, which submits every field on every save with no concurrency check — so a stale page wrote back a `true` that a deliberate act had cleared. See the "go-live gates" rule in [07-conventions.md](07-conventions.md).

> **Short domains: `pending` status + DB-enforced per-brand default (migration `0140`, B1).** Adds `'pending'` to the `short_domains_status_check` vocabulary and `is_default boolean NOT NULL DEFAULT false`, with partial unique index `short_domains_one_default_per_brand (org_id, brand_id) WHERE is_default`. Provisions `g.guidekn.com` (brand 8), `g.lumzen.co` (142) and `g.fitsyou.net` (143) as **`pending`** — matched by `brands.brand_id`, never a numeric id, and idempotent via `ON CONFLICT (org_id, domain) DO NOTHING`, so a re-run can never flip an activated row back. **Nothing mints under a pending row**: every layer of `resolveShortDomainForSend` requires `status='active'`, so even a pending row assigned as a per-number override falls *through* to the brand rather than failing the send. The `is_default` backfill flags the domain the pre-0140 rule already picked (`DISTINCT ON … ORDER BY created_at, id`, active only), so resolution is byte-identical — asserted across the full 108-pair (phone × brand) matrix by [`scripts/verify-brand-domain-resolution.ts`](../scripts/verify-brand-domain-resolution.ts) against a separately transcribed copy of the old rule. The index enforces **at most** one default per brand; "exactly one" is delivered by resolution falling back to oldest-active, because a brand with zero domains cannot be given a default (brands 142/143 are in that state until activated). ⚠️ Activating `g.lumzen.co` / `g.fitsyou.net` **enables tracked sending for those brands for the first time** — brand 142 and 143 have no active domain at all today.

> **`sends_enabled` audit verbs (migration `0139`, R4).** Widens `send_circuit_events_event_check` with `sends_enabled_on` / `sends_enabled_off`, so the `/settings/providers` toggle writes an audit row naming the actor — `sms_providers` has no `updated_at`, and without this the switch would be unattributable (the hole that made the 2026-08-13 `supports_api_send` reversion undiagnosable). **New verbs, not the breaker's `paused`/`resumed`:** those mean the latching circuit breaker tripped or a human cleared it, and reusing them would make an automated trip and an operator decision indistinguishable when reading the history back — the one thing this table exists to keep apart. The CHECK now carries three pairs for three questions: did a breaker trip, may this account API-send at all, does the operator want it sending right now. Additive, writes no rows, same shape as `0131`.

> **`links.short_domain_id` index (migration `0144`).** Non-partial btree, restoring the per-domain minted-link count on `/settings/short-domains` that #88 removed for cost. Measured on brand 8's three domains: **12,574 ms → 623 ms** in-database (`Seq Scan on links`, 3.28M rows, once per domain → `Index Only Scan`). Non-partial because the count must include a domain in ANY status — a `pending` host with links is exactly the case Delete must refuse, and a partial index would silently under-count. **Built `CONCURRENTLY` via [scripts/apply-links-short-domain-index-concurrent.ts](../scripts/apply-links-short-domain-index-concurrent.ts) BEFORE `db:migrate`**: `links` is written on every tracked send, so a plain `CREATE INDEX` would block minting for the whole build. The cost scales with LINK VOLUME, not domain count — gdkn.org alone carries 3,277,863 links — so if it becomes slow again, cap the count (exact up to N, "N+" beyond) rather than removing it a second time.

> **Per-carrier daily-cap index (migration `0143`, Q5).** Partial index `stage_sends (provider_phone_id, carrier_norm, sent_at) WHERE status = 'sent'`, supporting the once-per-batch cap counter. Without it the counter sequentially scans a 1.4M-row table on **every batch of every drain**, capped or not; with it the plan is an Index Only Scan. **Built `CONCURRENTLY` via [scripts/apply-carrier-day-index-concurrent.ts](../scripts/apply-carrier-day-index-concurrent.ts) BEFORE `db:migrate`** - `stage_sends` is large and hot, a plain `CREATE INDEX` takes `ACCESS EXCLUSIVE` and would block live sending, and `CONCURRENTLY` cannot run inside drizzle-kit's migration transaction. The migration file carries the plain `CREATE INDEX IF NOT EXISTS`, which then no-ops. Same pattern as `0101` / `0109`. The `daily_limit` column itself shipped with `0142`; this migration adds no column and writes no rows.

> **Per-number carrier policy (migration `0142`, Q4).** New table `phone_carrier_limits` — one row per `(org_id, provider_phone_id, carrier_norm)` carrying `allowed` and `daily_limit` (NULL = uncapped; the cap itself is Q5) — plus `provider_phones.allow_unknown_carrier boolean NOT NULL DEFAULT true`. **MACHINERY ONLY: the table ships EMPTY and the boolean true on all 35 numbers**, and because an ABSENT ROW MEANS ALLOWED AND UNCAPPED that state is a byte-for-byte no-op — asserted as an acceptance test. Enforced at **materialization** (the shared recipients builder), never as a skip at drain, so an excluded contact never becomes a `stage_sends` row. ANDs with the campaign-level `carrier_filter`, which is frozen into the pool at activation: each can only narrow, and the number's NO wins over the campaign's YES. RLS enabled with an org-scoped SELECT policy. See [07-conventions.md](07-conventions.md).

> **Per-NUMBER opt-out footer (migration `0141`, Q3).** `provider_phones.opt_out_footer text` — the most specific level of the footer chain (number > account > stage > `'Stop to END'`). Strictly additive, **ships NULL on all 35 numbers**, and has **no UI this run** (per-number editing lands with Q4/Q5); the column exists so the chain has no hole in its most specific slot. COMPLIANCE-BEARING: whatever wins the chain is the opt-out language that ships, and the kickoff gate validates the winner rather than any single field — so a value set here must contain a STOP keyword or the stage is refused (`missing_opt_out_language`).

> **Per-provider sending posture + STOP text (migration `0138`, R1).** `sms_providers.sends_enabled boolean NOT NULL DEFAULT true` and `sms_providers.opt_out_footer text`. Strictly additive and **inert on arrival** — nothing read either column in the deploy that introduced them (asserted by `scripts/verify-provider-sends-enabled-migration.ts`, which scans the seven send-path modules for a provider-qualified reference); R2 wires enforcement, R4 the admin panel. All 8 rows land `sends_enabled = true` / `opt_out_footer = NULL`, so behaviour is byte-identical. **Three flags on this table mean three different things and must never be collapsed:** `supports_api_send` = CAPABILITY (can this row send over an API at all — the go-live gate, audited); `sends_enabled` = POSTURE (should it, right now — a human's decision); `send_paused` = LATCH (an automated breaker tripped; needs a conscious human resume). Merging posture into the latch would make a breaker trip and an operator decision indistinguishable in the audit trail. `opt_out_footer` was inert on arrival and is **LIVE since Q3** — it is the ACCOUNT level of the opt-out footer chain (`provider_phones.opt_out_footer` > this > `campaign_stages.stop_text` > `'Stop to END'`), resolved by `resolveOptOutFooter` and validated by the kickoff gate as the text that actually ships. A value set here replaces the stage's STOP text on every message sent through the account, and must contain a STOP keyword or those stages are refused.

> **Per-phone short domain (migration `0137`).** `provider_phones.short_domain_id`, a nullable FK to `short_domains` with `ON DELETE SET NULL`. NULL - every pre-0137 row - means "no override, use the campaign brand's domain", which is exactly what kickoff did before. Resolution order is **phone override then brand default**, and the override must be org-owned **and** `status='active'`, so a `pending` domain can never be minted under. `SET NULL` rather than `CASCADE` is deliberate: removing a short domain must never delete an externally-provisioned sending number.

> **Short domains: one per brand limit removed (migration `0136`).** `short_domains_brand_id_uniq` (0052) enforced exactly one short domain per brand; it is replaced by a plain `short_domains_brand_id_idx`. Removing a restriction, not data: the single existing row and all 3,197,988 `links` rows are untouched. The cross-brand `short_domains_org_id_domain_unique (org_id, domain)` **stays** — two brands must never share a hostname, or the per-brand reporting split becomes meaningless and one brand's reputation damage bleeds into another's deliverability. Behaviour is unchanged until an operator adds a second domain: `lib/sends/kickoff.ts` picks `WHERE brand_id = … AND status = 'active' ORDER BY created_at, id LIMIT 1`, which is deterministic and already excludes non-active rows.

> **`sms_providers.adapter_code` (migration `0134`).** Splits the adapter lookup key out of `sms_provider_id`. That column is UNIQUE, so a second TextHub account could not reuse `txh` and became its own row under the invented code `txh2`, which the adapter registry special-cased back to the TextHub adapter. `adapter_code` carries the connection type (`txh2` → `'txh'`); `sms_provider_id` keeps being the row identity. Strictly additive: one nullable column plus a per-row backfill, no DROP, nothing rewritten. NULL means "no API adapter" — a real state, not missing data (`snx`, `smpl`). Cutover was staged: migration first, then `scripts/verify-adapter-code.ts` proving adapter resolution is object-identical via both columns for all 7 rows, then the drain switched to read `adapter_code`, and only then the registry alias removed.

> **Tells.co webhook capture (migration `0130`, Phase 1).** Creates `tells_webhook_events` and nothing else — additive, and inert until the Phase 3 routes exist. **The same FK-lock consideration as `0122`/`0124` applies**: it references `contacts` and `stage_sends`, so `CREATE TABLE` takes a `ShareRowExclusiveLock` on both hot tables — apply when the drain is idle. No provider-seed migration accompanies it: the `tls` `sms_providers` row (id 855) and its number/credential were created through the UI during Phase 0, so unlike `txr`/`ahi` there is no seeding SQL to point at. Design: `docs/superpowers/specs/2026-08-12-tells-provider-design.md`.

> **New indexes (migration 0093):** `stage_sends (sent_at, contact_id)` and `contact_contact_groups (contact_group_id, contact_id)` — support the twice-daily refresh's list-pressure/fresh-pool joins. The pre-existing `contact_contact_groups` PK is `(contact_id, contact_group_id)`, the wrong column order for "all contacts in a group."

> **Per-recipient group attribution (migration `0132`).** Before this migration, `offer_group_report_mv` built its rows by `unnest`-ing `offer_report_campaign_econ.group_ids` — a campaign targeting 12 groups contributed its WHOLE sends/revenue/sales/cost/optouts to all 12 rows, and the API route's `offerTotals` (summed from those same rows) inherited the same inflation, reading 10.2x the true total on one measured offer. `0132` rebuilds the group rows directly from `stage_sends ⋈ contact_contact_groups`, restricted to `offer_report_tracked_campaigns` (`link_mode='tracked'` only — a manual campaign's `sms_count` has no per-recipient row to attribute), and moves the footer to its own matview (`offer_report_offer_totals_mv`) read at offer grain instead of summed from the rows. The columns still don't foot — a contact in three groups is one send and three group-sends — but the non-additivity is now the correct, deliberate kind (the same rule migration `0128` applied to clicks) rather than an unbounded fan-out. See [04-features/offer-group-report.md](04-features/offer-group-report.md) and [07-conventions.md](07-conventions.md).

### Reports rollup (migration 0112)

Two pre-aggregated **hourly-bucket** fact tables feeding five reports (by number / offer / sequence message / hourly / group) over one shared metric set. Unlike the `0093` matviews (full `REFRESH CONCURRENTLY`), these are plain tables maintained by a **bounded 14-day rolling-window UPSERT** ([`lib/reporting/rollup.ts`](../lib/reporting/rollup.ts)). All bucketing is by the **SEND hour in America/New_York**; EPC / profit / rates are derived at READ time, never stored. See [04-features/reports-rollup.md](04-features/reports-rollup.md).

| Table | Grain / keys | Notes |
|---|---|---|
| `report_stage_hour` (Fact A) | PK(`org_id`, `stage_id`, `bucket_start_utc`) | one row per (org, stage, ET send-hour). Denormalized dims (`offer_id`, `brand_id`, `provider_credential_id`, `provider_phone_id`, `sms_provider_id`, `stage_number`, `behavioral_tier`, `funnel_stage`, `creative_id`) + counters (`sent_count`, `opt_out_count`, `click_count`, `offer_redirect_count`, `sales_count`, `revenue`, `cost`) + `settled`/`refreshed_at`. Feeds reports #1–#4; **grand totals always come from here.** ~302 rows all-time |
| `report_group_hour` (Fact B) | PK(`org_id`, `contact_group_id`, `stage_id`, `bucket_start_utc`) | same shape + `contact_group_id`. Feeds report #5. **Fans out** over `contact_contact_groups` (avg 1.34 groups/contact) — per-group numbers are truthful per group but sum to MORE than the true total by design (matches `offer_group_report_mv`). Never sum groups for a total. ~2,024 rows all-time |

> **Metric sources** (bucketed by the send's hour): sent = `stage_sends` (`status='sent'`); opt-outs = `opt_out_attributions` (via `stage_send_id`); clickers = clean human `clicks` (`classification='human' AND scored_at IS NOT NULL`, via `stage_sends.link_id`) — a DIFFERENT population than the Keitaro visit counter on `campaign_stages.click_count`; offer redirects = `stage_sends.offer_reached_at`; sales/revenue = **per-recipient** `stage_sends.converted_at`/`sale_revenue` (~93% of the authoritative `keitaro_stage_results` daily aggregate — the read layer surfaces the reconciliation delta); cost = `cost_per_sms × (sent + optouts)` per bucket. Number/cost resolve `COALESCE(stage_sends snapshot, stage live value)` for pre-0112 history.

> **Identity FKs only** (`org_id`/`stage_id`/`campaign_id`/`contact_group_id`, all `ON DELETE CASCADE`). Denormalized dimension keys are snapshots — deliberately NOT FK'd (same as `stage_sends.carrier_norm` and the `0093` matviews). No RLS on the fact tables; reads go through a server-side helper that filters `org_id` (same posture as the `0093` matviews). Partial index `(bucket_start_utc) WHERE settled=false` keeps the rolling-window settle sweep cheap at scale.


### Partner lead intake (migrations 0152–0154, Drip Phase 2)

Raw capture for partner-submitted leads. **Nothing consumes these tables yet** — Phase 2 stores and returns; the Phase 3 enrichment worker is the only thing that will move a row out of `status='received'`. See [04-features/partner-lead-intake.md](04-features/partner-lead-intake.md).

| Table | Grain / keys | Notes |
|---|---|---|
| `partner_keys` | PK(`id`), UNIQUE(`token`), UNIQUE(`org_id`,`partner_slug`) | One credential per partner. `token` is **plaintext and indexed** (addressing — it is resolved by equality before any org context exists); `secret_hash` is a **one-way SHA-256** (authentication). `sandbox` defaults **true**. Carries the per-key contract: `rate_per_sec`, `rate_per_day`, `max_payload_bytes`, `field_mapping` JSONB, `interest_tag` + `interest_tag_mode` (`force`/`default`). RLS + SELECT-only org policy. **Signed report links (0172):** `report_token_hash` (SHA-256, partial UNIQUE `WHERE NOT NULL` — the plaintext is returned once at issue and is unrecoverable), `report_token_issued_at`, `report_token_expires_at`, `report_show_revenue` (default **false**) |
| `lead_inbox` | PK(`id`), partial UNIQUE(`partner_key_id`,`dedup_key`) `WHERE dedup_key IS NOT NULL` | The raw payload in `raw` JSONB, plus addressing columns (`phone_e164`, `interest_tag`, `sandbox`). `normalized` stays NULL until Phase 3. `status` ∈ `received`/`processed`/`rejected`/`landline`/`duplicate`; index `(status, received_at)` is the worker's queue scan. `partner_slug` is denormalized and the FK is **ON DELETE RESTRICT** so provenance survives a rename and a key with leads cannot be deleted. RLS + SELECT-only org policy |
| `partner_key_usage` | PK(`partner_key_id`,`window_kind`,`window_start`) | Rate-limit counters. **Units differ by `window_kind`**: `sec` counts REQUESTS, `day` counts LEADS, `auth_fail` counts failed secret checks on a resolved token. `day`/`auth_fail` windows start at the **ET** calendar day. RLS + SELECT-only org policy |
| `alert_state` | PK(`alert_key`) | Generic state-transition gate for alerts (`ok`/`firing`). **Infra table: RLS on, NO policies**, same posture as `cron_locks`/`geoip_cache` |

> **⚠️ `alert_state.last_notified_at` is the DELIVERY marker, not a detection timestamp.**
> `state='firing' AND last_notified_at IS NULL` means *breach recorded, notification not yet
> delivered* — the next tick retries the send. It is stamped only after Telegram confirms
> receipt. No schema change was needed to introduce this: the column already existed, nothing
> reads it, and the previous code always stamped it on transition, so no historical row can sit
> in the pending state and be misread. See [lib/alerts/alert-state.ts](../lib/alerts/alert-state.ts).

> **⚠️ `dedup_key` is nullable by design.** The key is `(partner_key_id, phone, received_minute)` and phone is exactly what a malformed payload lacks; `NOT NULL` would make such a lead impossible to insert, rejecting the leads most worth capturing. Phone-less leads are stored with `status='rejected'` and a populated `error`.

> **⚠️ The rate-limit upsert carries a `WHERE` on its `DO UPDATE`**, so a refusal touches nothing and `RETURNING` yields no row. The bare counter shape (`campaign_tracking_counters`) increments unconditionally, which would let rejected retries burn a partner's daily quota. The `INSERT` branch is **not** covered by that guard, so the route pre-checks batch size — see [07-conventions.md](07-conventions.md).

The consumer side of [partner intake](#partner-lead-intake-migrations-01520154-drip-phase-2). See [04-features/drip-lead-enrichment.md](04-features/drip-lead-enrichment.md).

| Table | Grain / keys | Notes |
|---|---|---|
| `lead_events` | PK(`id`), partial UNIQUE(`inbox_id`) `WHERE inbox_id IS NOT NULL` | One row per lead that became a contact — WHEN it arrived, FROM WHOM, under WHICH tag. | `lead_intake_daily` | PK(`org_id`, `partner_key_id`, `day_et`, `interest_tag`) *(widened, 0171)* | Per-partner, per-**tag**, per-**ET**-day outcome counters: `received`, `mobile`, `voip`, `unknown`, `landline`, `rejected`, `duplicate`, `sandbox`, `lookups_spent`. ## Triggers & DB-side logic (in migrations, not Drizzle)
- **`handle_new_user()`** (`0001`): on `auth.users` INSERT, creates an `organizations` row + an `owner` `org_members` row.
- **`current_org_id()`** (`0001`): SECURITY DEFINER, backs RLS policies.
- **`segment_contacts` AFTER INSERT/DELETE trigger**: keeps `segment_stats.total_count` in sync.
- **`campaign_stages` BEFORE INSERT trigger**: auto-assigns `stage_number`.
- RLS policies per table across the security migrations (`0001`, `0021`, `0025`, `0028`, `0030`, …).
- **RLS enabled on every `public` table.** `geoip_cache` (infra cache, no `org_id`, server-only) has RLS enabled with **no policies** (migration `0066`) — the direct postgres-js connection and `service_role` bypass RLS, so server reads/writes keep working while anon/authenticated access is denied. Clears the Supabase advisor `rls_disabled_in_public`.
- **`stage_manual_sales` + `opt_out_attributions` RLS** (migration `0085`): both are tenant tables (`org_id`) written only by the privileged server connection but read org-scoped by the Reports tab, so each gets an `org_id = current_org_id()` **SELECT** policy and no write policies — mirroring `stage_sends` (`0050`). Second `rls_disabled_in_public` remediation after `geoip_cache`.
- **`record_exposure_on_sent()` + two `stage_sends` triggers** (migration `0086`): `AFTER INSERT WHEN status='sent'` and `AFTER UPDATE OF status WHEN status='sent' AND OLD.status IS DISTINCT FROM 'sent'` — share one SECURITY DEFINER function that resolves the creative (via stage) + offer (via campaign) and inserts into `creative_exposures` / `offer_exposures` (`ON CONFLICT DO NOTHING`). Fires from every path that sets `'sent'`, so no send path can bypass the ledger.
- **`bump_offer_exposure_count()` + `offer_exposures` AFTER INSERT trigger** (migration `0086`): upserts `offer_exposure_counts.distinct_contacts += 1`. Fires only on genuinely-new (org, contact, offer) rows. Same junction-trigger shape as `segment_stats.total_count`.
- **`creative_exposures` / `offer_exposures` / `offer_exposure_counts` RLS** (migration `0086`): tenant tables written only by the server connection / SECURITY DEFINER triggers; each gets an `org_id = current_org_id()` SELECT policy and no write policies (0085 precedent).
