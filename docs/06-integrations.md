> **Deploy region — ALL functions run in `fra1`, co-located with the DB (moved 2026-07-30).**
>
> The project-level setting is the **only** thing that controls placement: `serverlessFunctionRegion = "fra1"` / `defaultResourceConfig.functionDefaultRegions = ["fra1"]`. **Per-route `export const preferredRegion` does NOTHING here** — Fluid Compute (`fluid: true`) takes placement from the project setting and ignores segment exports. Five routes still carry a `preferredRegion = "fra1"` export from 2026-07-13; they are **dead config** that happens to agree with the project setting. Don't add more, and don't trust one to move a route.
>
> **How to verify placement (no deploy needed):** `x-vercel-id` is `<edge-pop>::<compute-region>::<id>`, and an unauthenticated 401 still executes the function, so any route is a safe probe:
> ```
> curl -sD - https://camman.vercel.app/api/clicks/score-pending -o /dev/null | grep -i x-vercel-id
> #  arn1::fra1::…   <- second segment is where the function ran
> ```
>
> **Why the move.** Per sequential DB query, measured: **iad1 → 187 ms, fra1 → 2.1 ms (89×)**. Nothing about the DB changed — that was pure transatlantic round-trip tax, paid on every query, for queries whose server-side execution is often <1 ms.
>
> **The `/r/[code]` question was measured, not assumed.** The old note here asserted US-facing routes had to stay in the US. That was wrong: the redirect makes **2 sequential DB round trips** (link lookup → click insert, strictly dependent, both awaited) for **0.86 ms** of actual DB work, so from `iad1` it burned ~374 ms of network per click. Moving to `fra1` trades those two transatlantic crossings for **one** PoP→function hop. TLS terminates at the **edge PoP**, not the function region (measured: TCP connect 14 ms / TLS 68 ms from Poland — it would be ~110/330 ms otherwise), so handshake cost does **not** move with the region. Modelled for a US handset: **~400 ms → ~115 ms**.
>
> Keep it **single**-region. Pro allows a multi-region list, but with one DB in `eu-central-1` extra regions would just strand some instances transatlantic again.
>
> `maxDuration` was **not** lowered alongside the move — the extra headroom is left as-is.

> Telnyx gotchas (`lib/telnyx/`): `carrier.type` has **no `landline` value** — its enum is libphonenumber's (`fixed line`, `mobile`, `voip`, `fixed line or mobile`, `toll free`, …). Map `fixed line`→landline, prefer `portability.line_type` (port-corrected) over `carrier.type`, and send anything exotic/ambiguous to `unknown` (which stays **eligible** — never silently suppress). We request a single `type=carrier` (the repeat-vs-array param syntax is ambiguous in Telnyx's own docs, but moot for one value). `/v2/balance` returns **strings**, not numbers — parse before comparing; gate on `available_credit`. **403 code 10038** = account-level feature gate → alert, do NOT retry. **Negative balance disables lookup** on Telnyx's side (402-class) → pause the batch + Telegram alert, never retry-loop. Rate limits are undocumented → configurable concurrency (default 10 rps) with exponential backoff on 429. Normalize every number to E.164 `+1XXXXXXXXXX` (via `lib/phone-validation.ts`) before the call **and** before writing `phone_lookups.phone`, so the global cache joins `contacts.phone_number` and never double-pays. Pricing has a **mobile-only** surcharge (base LRN + carrier only on mobile results); rates are admin-editable in `lookup_settings` because Telnyx exposes no pricing API.

> Keitaro gotchas (`lib/keitaro/`): point all calls at the single admin host `KEITARO_API_URL` (default `https://admin.gdkn.org`) — never a brand tracking domain. Group reports by `sub_id_3` + `campaign_id`, where `sub_id_3` carries the **stage tracking id** (not a bare campaign id), so mapping back is `sub_id_3` → `campaign_stages.tracking_id`. The `campaign_id` dimension separates landing-page **visits** (campaign **name** `gk-lp-visits` — its alias is a random code, so match on name not alias) from **offer redirects** — resolve the name → `campaign_id`(s) via `GET /admin_api/v1/campaigns`, never a hardcoded id (rebuild-safe). Keep `admin.gdkn.org` DNS-only / WAF-excepted so the every-5-min calls aren't bot-challenged. The documented grouping/metric keys live in one place (`KEITARO_GROUPING` / `KEITARO_METRICS` in `lib/keitaro/client.ts`) — a wrong key silently returns nothing. **Conversions log** (`conversions/log`, per-recipient sales): returns **only** the `columns` you request and **400s on any unknown column name** (unlike report/build, which silently drops); it also rejects an `order` key (sort in memory). Confirmed columns: `event_id` (unique conversion id, UUIDv7 — the dedup key), `sub_id_1` (= recipient `stage_sends.id`), `status` (`lead`/`sale`/`rejected`, lowercase), `revenue` (NOT `payout` — doesn't exist), `datetime` (ET wall-clock). Pinned in `KEITARO_CONVERSION_COLUMNS`. **Clicks log** (`clicks/log`, per-recipient offer-page reach — Level 2): same `events` report schema / 400-on-unknown-column contract. Confirmed columns: `event_id` (per-click id, dedup key), `sub_id_1` (recipient id), `campaign` (NAME — `gk-lp-visits` ⇒ landing/L1, dropped; any other ⇒ offer/L2), `campaign_id`, `datetime` (ET). Filter `sub_id_1 NOT_EQUAL ""` server-side. Pinned in `KEITARO_CLICK_COLUMNS`.

> Ahoi gotchas (`lib/sends/providers/ahoi.ts`): the platform **always returns HTTP 200** — never trust the HTTP status, classify off the body `status` field only. Numbers are 10-digit with no `+1` on the wire in both directions (`toAhoiRecipient`/re-add `+1` on the way back). Portal "Enforce GSM/160" settings have no effect — Ahoi silently sends Unicode and splits messages over 160 chars into billed segments, which is why the segment-count preflight gate (`lib/sends/segments.ts`, G8) exists. Webhook registration is **manual, not API-driven** — Phase 0 recon found no Ahoi equivalent of TextHub's `registerOptOutCallback`. `scripts/seed-ahoi-webhook-token.ts` mints `provider_credentials.inbound_webhook_token` (idempotent) and prints both webhook URLs (`/api/webhooks/ahoi/dlr/<token>`, `/api/webhooks/ahoi/inbound/<token>`) — the SAME token authenticates both paths (the URL path, not the token, distinguishes DLR vs inbound) — for the operator to paste into the Ahoi/api19 portal by hand.

> Text Request gotchas (`lib/sends/providers/textrequest.ts`, `lib/sends/textrequest-*.ts`). The API contract was established by reading the live API against its OpenAPI spec (`https://www.textrequest.com/dist/swagger/apiv3docs.json` — the docs page itself is client-rendered and yields nothing to a fetcher); `scripts/probe-textrequest-api*.ts` are the read-only recon scripts. **Unknown query params are SILENTLY IGNORED, not rejected** — this is the dangerous one: a poll built on a guessed param name (`start`, `startDate`, `since`) believes it asked for a 6-hour window and instead receives the account's entire history. The documented, verified names are `start_date`/`end_date` (messages) and `has_opted_out` / `is_suppressed` / `last_message_received_after` / `contact_phone_number` (contacts). Always prove a param NARROWS the result set before depending on it. **Every timestamp (`message_timestamp_utc`, `opted_out_utc`, …) is UTC but carries NO `Z` and no offset** — `new Date(...)` on it silently applies the server's local zone (same bug class that zeroed stage opt-out counters when TextHub's Mountain-time `received_at` was read as UTC); parse via `parseTxrUtcTimestamp`. Collections are always `{items,meta:{page,page_size,total_items}}` with **0-based** `page` (Phase 1's healthcheck guessed a `data` wrapper and so parsed zero dashboards off a healthy 200); `limit` is ignored, `page_size` is honored. Messages default to **oldest→newest**, but an **undocumented `sort` param IS honored** (`sort=desc` / `asc`, verified live 2026-08-21 — it composes with `message_direction` and with paging, and an unrecognized value is rejected with **HTTP 400** rather than silently ignored, so it is safe to depend on: a future removal fails loudly). The poll therefore asks for `sort=desc` and walks pages FORWARD from the newest, keeping `planTxrPageWalk` (page 0 for `total_items`, then backwards) as the fallback if `sort` is ever refused. **`page_size` is silently CLAMPED at 1000** (2000 and 5000 both return 1000 rows and echo `meta.page_size=1000`), so 1000 is the ceiling worth asking for. **Outbound and inbound are walked SEPARATELY** (`message_direction=S` / `R`), each with its own 20-page budget = 20K messages per direction: on 2026-08-21 dashboard 68093 sent 10,000 messages in 46 minutes and overflowed the shared 10K budget at 21 pages, and under one budget a big campaign can push STOP replies out of the read. Because unknown params are silently ignored, the per-row `message_direction` checks stay in the poll as the real guard — if the server-side filter ever stopped working both walks would simply see every row and capture would dedupe the overlap. There is no per-message GET (`/messages/{id}` 404s) and `?message_id=` is ignored, so a single message's status is only readable via the list. **CamMan OWNS the opt-out footer — Text Request does NOT append one on API `/messages` sends** (proven live 2026-08-12: our API send's TR message record carried no footer; the footer on earlier messages was typed in-body or added only by the TR *portal* UI, never by the API). The earlier "TR auto-appends" belief was a misattribution of portal behavior. CamMan renders the footer INTO the body via the stage's `stop_text` — **txr uses the same system-wide `stop_text` default (`Stop to END`) as every other provider; there is no txr-specific footer wording** — and the G8 kickoff gate ENFORCES opt-out language for txr — refusal `missing_opt_out_language` when `hasOptOutLanguage(body)` is false (a `\bstop\b` check on the effective rendered body); **other API providers dry-run this check** (log + Telegram, no refusal) for a 30-day window before enforcement widens. Segment math counts the actual rendered body (no phantom appended footer). **Account webhooks are disconnected by TR after 10 consecutive non-2XX/3XX responses** (`is_connected:false`) and go silent with no error; the webhook routes therefore ALWAYS return 200 (even on a processing failure, which alerts to Telegram instead), and `/api/cron/textrequest-poll` re-checks `is_connected` every tick and reactivates via `PUT`. Webhook payloads carry NO event name and are shaped inconsistently (`msg_received` nested camelCase, `contact_updated` flat snake_case), so hooks are registered with an `?e=<event>` hint and shape detection is the fallback. `msg_sent` and `msg_received` share one payload schema — only `conversation.messageDirection === 'R'` is an inbound reply, and mistaking our own outbound copy for a reply would keyword-match the "Text STOP to opt out" footer we just sent. Error-code vocabularies differ by channel: send-time `30003/30004/30005/30006/30050`, delivery-status `1002/2000/2002/2100/3000`; **2100 and 30050 both mean "contact has previously opted out"** and 2002 means carrier-filtered/spam (not an opt-out). Hook registration is API-driven (unlike Ahoi's manual portal paste) but deliberately **operator-triggered** — `POST /api/providers/[providerId]/credentials/[credentialId]/register-textrequest-hooks`, which also mints the per-credential `inbound_webhook_token` that the drain's `status_callback` threading needs (no token ⇒ no callback is requested at all, and only the poll reconciles).

> TextHub gotchas (`lib/sends/texthub.ts`): never pass `long_url` (their rewriter clobbers our tracked link) or `group` (share link — kills per-recipient uniqueness). **`sender` param (2026-07-22)** selects the send-from number: value = **national digits, no country code** (10 digits for 10DLC/TFN; short codes 5–6 digits as-is), derived from the stage's `provider_phone_id` via `toTexthubSender()` — never `libphonenumber` (throws under `tsx`, same reason Ahoi hand-rolled `toAhoiRecipient`). `sender` is optional to TextHub itself (omitted ⇒ their account default), but CamMan never omits it deliberately: a stage with no sender number is refused before send (`no_sender_number` at kickoff, `lib/sends/preflight.ts` checklist, and the adapter's own refuse-on-null as a last backstop) rather than falling through to TextHub's account default — see [04-features/sms-send-pipeline.md](04-features/sms-send-pipeline.md). Their push opt-out callback is broken on their side → intake uses inbox **polling**. **Inbox is hard-capped at the 200 most-recent messages with no pagination/cursor** — during a STOP-reply burst (peak days ~1,400 opt-outs) more than 200 could arrive between polls, so the oldest scroll off the window permanently before ingest. Result: the opt-out poller silently under-captured (~30% loss over Jun 29–Jul 5; 46% on the Jul 4 peak). **The poll cadence was tightened from `*/15` to every 5 min on 2026-07-19** to shrink this window 3× — a mitigation, not a cure (a >200 burst inside 5 min still overflows). Remediation until TextHub adds pagination/a working push callback: export the full inbox CSV and run a **backfill** (see CHANGELOG 2026-07-06) that re-imports the missing `YES` rows with the same semantics as the poller (org-wide `opt_outs` + live-72h stage attribution), deduped against `texthub_inbound_events` by `(phone, received_at)`. **`pollOptOuts` (`lib/sends/poll-opt-outs.ts`) is TextHub-only** — its credential selection (`selectPollableCredentials`) filters on the **CONNECTION TYPE**, `sms_providers.adapter_code = 'txh'`, not on `supports_api_send` and not on the row identity. (It filtered `sms_provider_id IN ('txh','txh2')` until migration `0134` split type out of identity; enumerating identities was always the fragile form — a third TextHub account would have had to be added to the list by hand, and `adapter_code` matches every row of the type whatever code it carries. Both TextHub rows — `txh` id 2 and `txh2` id 499, a second account modeled as its own provider row hitting the same inbox API — share `adapter_code='txh'` and are both polled; `scripts/test-stop-intake-ungated.ts` asserts the selected set is exactly the credentials of every `adapter_code='txh'` row **and** that it spans more than one row.) Before 2026-07-15 the WHERE clause matched any api-send-capable provider, so once Ahoi (`sms_provider_id = 'ahoi'`) was seeded with `supports_api_send = true`, its `api_key` got fired at TextHub's `?inbox=true` URL, 404'd, and raised a false "Opt-out poller FAILED" Telegram alert. Ahoi has its own opt-out intake (`lib/sends/ahoi-optout.ts`, `ahoi-dlr-optout.ts`, `ahoi-inbound.ts`) — any future non-TextHub api-send provider must NOT be added to this poller's filter.

### Connection-type descriptors (`GET /api/provider-types`)

Each adapter in `lib/sends/providers/` carries a static, secret-free `descriptor` (`ProviderDescriptor`, `lib/sends/providers/types.ts`) describing what the connection type is and which credential fields it needs. `GET /api/provider-types` serves the canonical list — membership + `providers.view`, no DB read, no org scoping, no secrets. It exists so a provider account is created by **picking a connection type** rather than typing the short code from memory: a mistyped `sms_provider_id` used to produce a provider row that only failed at drain time, with `UnknownProviderError`, after the campaign was already activated.

`credentialFields` describes what to **ask for**, never what is stored. `descriptor.validateCredentials` is the non-sending credential check behind the uniform Test-connection action.

**`descriptor.notes: string[]` (R3) is the operator-facing "About this provider" copy** rendered on `/settings/providers` and served as `notes` on `GET /api/provider-types` (always an array, never null). It is **code-owned, not a DB column**, deliberately: a note describes how a connection TYPE behaves, which is a property of the adapter and changes only when the adapter does. A DB column would let the two drift, and an operator editing "TextHub returns failures as 404" would be editing a fact rather than a preference. Three rules, pinned by `scripts/test-provider-descriptors.ts`: every note must be **true of that type and verifiable from the code or a probe script** (an operator will act on it), **operationally useful** rather than adapter trivia, and **never a secret or a value** — the test rejects any credential-shaped substring and any note under 20 characters. `PER_NUMBER_RATE_NOTE` is defined once in `types.ts` and spread into all four descriptors (asserted present on each) because it is true of every type and operators reliably look for the per-second rate on the provider, where it is not: that rate lives on `provider_phones.max_sends_per_second`, and only the per-run / per-minute / 24h volume ceilings are account-level.

| Connection type | `can_validate` | Non-sending check |
|---|---|---|
| TextHub (`txh`) | yes | inbox read (`?inbox=true`) via the existing `fetchInbox` |
| Ahoi (`ahi`) | yes | same-day CDR pull; **body-classified**, see below |
| Text Request (`txr`) | yes | `GET /dashboards` via the existing `textrequestHealthcheck` |
| Tells (`tls`) | **no** | none exists — its only endpoint sends |

**One uniform check, three states.** `POST /api/providers/[providerId]/credentials/[credentialId]/test-connection` runs the descriptor's check for any account — admin+ (`provider_credentials.manage`), read-only at the provider, **not** gated by `SEND_ENABLED`. It returns `state: "valid" | "invalid" | "unknown"` plus optional `discovered` items. This replaced the txr-only `…/healthcheck` endpoint, which was deleted; Text Request's dashboard ids now travel in `discovered` so binding a `dashboard_id` to a number still works from the same dialog. When `can_validate` is false the UI shows explanatory text instead of a button.

**Two provider-specific actions stay separate and are now gated server-side.** `…/credentials/test` (a real send — spends money) and `…/register-callback` (mutates remote state at TextHub) are TextHub-only because both routes call TextHub's client directly, declared as `supportsTestSend` / `supportsOptOutCallbackRegistration` on the descriptor. Until P2 the restriction lived **only in the client component**: a direct request with an Ahoi, Text Request or Tells credential reached TextHub's API carrying that account's key, and `register-callback` would additionally mint an `inbound_webhook_token` on a credential whose provider never uses that webhook path. Both routes re-check the descriptor now; `scripts/test-provider-action-gates.ts` proves the rejection with real authenticated requests. Note the send-test route checks the connection type **before** `SEND_ENABLED`, so a misrouted request gets the correct error and the gate stays provable without arming sending.

**Per-number settings come from the descriptor.** A connection type declares `phoneSettingFields` (name, label, placeholder, help); `name` must match the `provider_phones` column the input binds to. The provider detail response resolves them from `adapter_code` and returns `phone_setting_fields`, so the phone form renders them without importing the registry. Text Request declares `dashboard_id`; no other type declares any today. This replaced a hardcoded `providerKey === "txr"` gate that keyed on row identity — under it a second account of a type would not have received its type's fields.

**Creating a provider picks a type; the code is derived.** `GET /api/provider-types` also returns `existing_providers` per type (org-scoped), and `POST /api/providers` takes `connection_type` instead of a typed `sms_provider_id`. The code is derived from the registry, shown **read-only but visible** (it appears in drain errors and reports, so operators need to recognise it). `POST /api/provider-types/[key]/validate` checks credential values that aren't stored yet; nothing is persisted.

**Picking a type that already exists is refused, never auto-suffixed.** The server answers **409 `connection_type_exists`** with the existing rows attached, and the UI steers to *add an account to that provider* — a second provider row splits that provider's pacing counters and reporting in two, which is the cost `txh2` already imposes. A genuinely separate row stays possible but must be deliberate: `create_separate_row: true` **plus** an explicit distinct code, which is rejected if it collides with a registry key. Silent auto-suffixing is what produced `txh2`; the picker must not reproduce it. The check is alias-aware — asking for TextHub reports both `txh` and `txh2` (`registryKeysForType`). Enforced server-side and proven by `scripts/test-provider-create-collision.ts`.

Provider creation does **not** collect a credential: creation and credential entry stay separate steps, and the operator lands on the provider page where Test connection works against a real stored account.

`txh2` is an **alias**, not a connection type: a second TextHub *account* modeled as its own provider row because `sms_provider_id` is `UNIQUE`. `getDescriptor("txh2")` resolves to the TextHub descriptor; `listConnectionTypes()` excludes it so TextHub appears exactly once in a picker. The alias set retires when `adapter_code` lands.

**Ahoi's check is body-classified because nothing else works.** Measured 2026-08-17 (`scripts/probe-ahoi-badkey.ts`, kept as the regression reference): `GET /cdrs/download/csv` returns **HTTP 200 for every case** — valid, wrong, bogus and empty key — and `Content-Type: text/html` even for the successful CSV. Status and content type are both useless. Classification: body parses as JSON with `status:"error"` ⇒ invalid (key off `status`, **never** the message — a wrong key says `not logged in`, an empty one says `invalid key`); body starts with the CDR header `date,your_cost,…` ⇒ valid; anything else ⇒ **unknown**. Never classify on CSV row count — a valid key on a zero-traffic day returns 0 data rows, identical to a failure.

### Secrets handling rules (CLAUDE.md §11)
- Never commit `.env.local` or any populated secrets; never log secrets or put them in error messages.
- The TextHub/Ahoi `api_key` is **not** an env var — it's stored per provider, per-account (migration 0110 made `provider_credentials` multi-account: N credentials per provider, each a row) in `provider_credentials`, **AES-256-GCM-encrypted at rest** (`api_key_encrypted`, keyed by `PROVIDER_CREDENTIALS_KEY`; protected by deny-by-default RLS + app-layer permission checks as defense-in-depth). See [security-notes.md](security-notes.md) and [07-conventions.md](07-conventions.md). The legacy plaintext `api_key` column is retained only for a dual-read window until a later, separately-gated migration drops it. The blob's leading `v1.` version segment is the rotation seam for a future master-key rotation (`v2.` alongside `v1.`, no big-bang re-encrypt required).
- Production env vars are set in the Vercel dashboard (Settings → Environment Variables), not via CLI.
